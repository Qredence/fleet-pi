Each `chat-postgres-*.ts` file is a self-contained migration unit exporting two constants: a stable `*_MIGRATION_ID` string (used as an idempotency key) and a `*_SQL` template literal containing the DDL/DML to apply. The entry point `chat-database-url.ts` resolves the connection URL from either `FLEET_PI_CHAT_DATABASE_URL` or `DATABASE_URL`. `chat-postgres-schema.ts` is the canonical schema definition that creates all tables (`pi_sessions`, `pi_session_entries`, `pi_runs`, `pi_run_events`, `pi_tool_executions`, `pi_file_mutations`, `pi_user_providers`, `pi_user_settings`, `pi_session_tombstones`) and initial RLS policies using `current_setting('app.current_user_id', true)`. Subsequent migrations evolve the schema and security posture: `chat-postgres-data-api-auth.ts` introduces `fleet_pi_current_user_id()` to bridge Neon's `auth.user_id()` JWT with the legacy `app.current_user_id` GUC; `chat-postgres-force-rls.ts` applies `FORCE ROW LEVEL SECURITY` on every table; `chat-postgres-rls-initplan.ts` and `chat-postgres-rls-strict.ts` rewrite policies to wrap `current_setting` in a subquery for init-plan evaluation; `chat-postgres-provider-auth.ts` adds `auth_type`/`encrypted_payload` columns; `chat-postgres-session-tombstones.ts` adds soft-delete tracking; `chat-postgres-user-settings.ts` creates per-user JSONB settings; `chat-postgres-db-optimization.ts` drops unused indexes and adds constraints; `chat-postgres-ownership-execute-revoke.ts` tightens function EXECUTE grants; and the revoke migrations (`data-api-revoke.ts`, `data-api-revoke-again.ts`) strip broad `authenticated`/`anonymous` privileges so only `fleet_pi_app` can access data. Dependency direction is strictly one-way: migrations are applied in order by their IDs and never import each other.
