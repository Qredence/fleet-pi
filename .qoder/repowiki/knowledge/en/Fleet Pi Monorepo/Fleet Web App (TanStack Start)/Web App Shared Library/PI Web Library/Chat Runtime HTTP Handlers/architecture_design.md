The module is organized as a thin HTTP surface over shared PI server logic. `router.ts` is the single entry point (`handleChatRuntimeRequest`) that dispatches incoming `Request` objects to per-endpoint handlers based on method + pathname under `/api/chat/*`, wrapping every call in `runWithChatAuthSurface('neon-function', ...)` for authentication and applying CORS via an allowlist from `FLEET_PI_CHAT_RUNTIME_CORS_ORIGINS`. Each handler lives in `handlers/*.ts` (new, post-chat, question, resume, abort, run, runs, session, sessions) and follows a uniform shape: parse/validate input (often via Zod schemas from `@workspace/pi-protocol/chat-protocol.zod`), authenticate with `withAuthenticatedChatRequest`, enforce ownership through `enforceChatSessionOwnership`, then delegate to pure functions in `@/lib/pi/server` (e.g. `createNewChatSession`, `abortActiveSession`, `hydrateChatSession`). Streaming endpoints like `post-chat` return NDJSON `ReadableStream`s via `handleChatTurn` and `encodeEvent`, while non-streaming handlers use `wrapApiHandler` or try/catch blocks that map errors to JSON responses using `getResponseStatus` and `getErrorMessage`. The dependency direction is strictly inward: handlers → `@/lib/auth/chat-api-auth` → `@/lib/pi/server` / `@/lib/db/*` / `@/lib/pi/provenance-query`; nothing in this module is imported by the rest of the app except the router's export.
