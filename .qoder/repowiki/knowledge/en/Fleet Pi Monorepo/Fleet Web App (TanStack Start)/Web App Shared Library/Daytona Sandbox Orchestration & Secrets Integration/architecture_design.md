The module is organized as a layered toolkit around `@daytona/sdk`:

- `client.ts` provides a thin, typed wrapper over the Daytona SDK (create/start/stop/delete sandbox, file upload/download, command execution, snapshot/volume management) with uniform `DaytonaError` handling.
- `sandbox-operations.ts` adapts those primitives into the `BashOperations`, `ReadOperations`, `WriteOperations`, `EditOperations`, `GrepOperations`, `FindOperations`, `LsOperations` interfaces consumed by the coding agent, enforcing path-bound security via `assertPathWithinWorkspaceBound`.
- `user-sandbox.ts` is the high-level orchestrator: it caches one sandbox + volume per `userId`, deduplicates concurrent provisioning requests, decides whether to reuse or recreate based on health, mount layout, and secrets fingerprint, and exposes lifecycle helpers (`releaseUserSandbox`, `destroyUserSandbox`).
- Supporting modules handle cross-cutting concerns: `sandbox-prepare.ts` builds the bootstrap shell script that clones the repo, migrates legacy layouts, and writes auth files; `sync-daytona-secrets.ts` upserts provider API keys into Daytona org Secrets with host allowlists and falls back to plaintext injection when the Secrets API is unavailable; `secret-hosts.ts` declares which providers are eligible and resolves their HTTPS hosts; `refresh-sandbox-credentials.ts` pushes updated credentials into a live cached sandbox or triggers a recreate; `tool-context.ts` tracks session→userId mapping for tool calls.
- Dependency direction flows inward: `user-sandbox` → `client` + `sandbox-prepare` + `sync-daytona-secrets` + `sandbox-provider-secrets`; `sandbox-operations` depends only on `client`; nothing imports from the broader app except shared contracts like `workspace-contract`.
